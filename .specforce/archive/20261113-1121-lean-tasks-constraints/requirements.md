# Feature: Lean Tasks, Design-Anchored Decisions

## 1. Context & Value
Task roadmaps generated by the kit are verbose because every task is forced to carry a minimum number of implementation steps, which turns the roadmap into code written as prose and duplicates what the design and the code already say. This feature makes the step list optional and lean, gives implementation decisions a proper home in the design, and keeps workers fully informed by delivering the relevant design excerpt with each task, so specifications get shorter without losing the context an implementer needs.

## 2. Out of Scope (Anti-Goals)
*Explicitly state what MUST NOT be built in this specific feature to prevent scope creep.*
- Do not change the requirements template, its per-story UI/UX and NFR blocks, section numbering, or the rule about asking before writing unsourced numbers (separate specification).
- Do not change delta declaration, sealing, greenfield module handling or the module-impact section (separate specification).
- Do not remove or weaken the mandatory acceptance check, the traceability link to requirements, the parallelism rules or the black-box verification phase.
- Do not change batch budgets, correction cycles or QA tiers of the implementation flow.
- Do not rewrite or migrate specifications that already exist; they must keep working as they are.

## 3. Acceptance Criteria (BDD)
*Every requirement MUST be testable. Define success and failure.*

### [US-1] Optional, Lean Task Constraints
**User Story:** AS A spec author, I WANT TO write tasks that state target, requirement link, optional constraints and an acceptance check, SO THAT roadmaps stay short and do not restate decisions already in the design.

**Scenarios:**
1. **[Happy Path]** GIVEN a task with a target, a requirement link and an acceptance check but no step or constraint list WHEN the roadmap is validated THEN it is accepted.
2. **[Happy Path]** GIVEN a task that lists constraints WHEN the roadmap is validated THEN the constraints are accepted with no minimum or maximum count enforced.
3. **[Edge Case]** GIVEN a task with no acceptance check, no target or no requirement link where one is mandatory for the spec size WHEN the roadmap is validated THEN it is rejected with a message naming the task and the missing field.

**UI/UX Specifics:**
- **View/Component:** Roadmap validation output of the specification status report.
- **Feedback Logic:** Errors name the task identifier, the line and the missing field; a roadmap without constraints produces no message about constraints.
- **Keybindings:** Not applicable.

**Technical Constraints (NFR):**
- **[Performance]:** Validation stays a single pass over the roadmap with no added cost relative to today.
- **[Integrity]:** The planning guidance for tasks asks for constraints only when they carry something the implementer could not deduce from the design and the code (a pitfall, a deviation from repository convention, or a decision recorded in the design, referenced rather than repeated), and forbids method signatures, constants and code snippets in tasks.

### [US-2] Existing Specifications Keep Working
**User Story:** AS A maintainer with archived and in-flight specifications, I WANT TO keep using roadmaps written with the previous step list, SO THAT nothing already planned or archived breaks.

**Scenarios:**
1. **[Happy Path]** GIVEN a roadmap whose tasks use the previous step-list heading with any number of items WHEN it is validated and its tasks are read for implementation THEN it is accepted and its items are delivered to workers as the task's constraints.
2. **[Edge Case]** GIVEN a task that has the previous heading but no items under it WHEN the roadmap is validated THEN it is accepted, since the step list is no longer mandatory.
3. **[Edge Case]** GIVEN a roadmap that contains both headings in different tasks WHEN it is validated THEN each task is evaluated on its own and the roadmap is accepted.

**UI/UX Specifics:**
- **View/Component:** Specification status and implementation status reports.
- **Feedback Logic:** No migration prompt or deprecation error is shown for the previous heading.
- **Keybindings:** Not applicable.

**Technical Constraints (NFR):**
- **[Performance]:** No measurable change for existing roadmaps.
- **[Reliability]:** Every roadmap that was valid before this feature remains valid after it.

### [US-3] Non-Blocking Warnings Against Pseudo-Code in Tasks
**User Story:** AS A spec author, I WANT TO be warned when a task drifts into implementation detail or grows too large, SO THAT I can trim it before approval without being blocked by false positives.

**Scenarios:**
1. **[Happy Path]** GIVEN a task containing a fenced code block WHEN the specification status is requested THEN a warning names the task and the reason, and the specification is still reported as valid.
2. **[Happy Path]** GIVEN a task whose target and constraints together cite more than three distinct file paths WHEN the specification status is requested THEN a warning names the task and the paths count, and the specification is still reported as valid.
3. **[Edge Case]** GIVEN a task with neither signal WHEN the specification status is requested THEN no warning is produced for it.
4. **[Edge Case]** GIVEN a roadmap with several flagged tasks WHEN the machine-readable status is requested THEN every warning is listed separately and none changes the validity result.

**UI/UX Specifics:**
- **View/Component:** Specification status report, human and machine-readable forms.
- **Feedback Logic:** Warnings are visually and structurally distinct from errors and appear after them.
- **Keybindings:** Not applicable.

**Technical Constraints (NFR):**
- **[Performance]:** Warnings are computed in the same pass as validation.
- **[Integrity]:** Warnings never alter the validity result, the progress figure or the exit outcome of any command.

### [US-4] Workers Receive the Design Context of Their Task
**User Story:** AS A developer running the implementation flow, I WANT TO have each worker receive the design entries that concern its task, SO THAT a lean task still gives the worker everything needed without reading the whole design.

**Scenarios:**
1. **[Happy Path]** GIVEN a task whose target appears in the design inventory or contracts WHEN the orchestrator prepares the worker brief THEN the brief contains that inventory entry, the related contract and any recorded rationale, together with the task's constraints and acceptance check.
2. **[Edge Case]** GIVEN a task whose target has no matching design entry, or a specification without a design WHEN the brief is prepared THEN the brief omits the design excerpt, states that none applies, and does not invent one.
3. **[Edge Case]** GIVEN a task with no constraints WHEN the brief is prepared THEN no empty constraints line is shown.

**UI/UX Specifics:**
- **View/Component:** Worker brief produced by the implementation flow.
- **Feedback Logic:** The brief names the design source of each excerpt so a worker can read the full entry if needed.
- **Keybindings:** Not applicable.

**Technical Constraints (NFR):**
- **[Integrity]:** Excerpts are copied from the design as written; the brief never paraphrases or extends them.
- **[Reliability]:** A missing or unreadable design never blocks the brief.

### [US-5] Implementation Rationale Lives in the Design
**User Story:** AS A spec author, I WANT TO record a one-line reason for each non-obvious technical decision inside the design contract or inventory entry it affects, SO THAT decisions have one authoritative place and tasks can point to it.

**Scenarios:**
1. **[Happy Path]** GIVEN a non-obvious decision such as accepting an additional input channel or resolving an entity by one attribute instead of another WHEN the design is written THEN the affected contract or inventory entry carries a one-line reason.
2. **[Edge Case]** GIVEN a decision with no real alternative WHEN the design is written THEN no rationale line is added.
3. **[Edge Case]** GIVEN a design being written WHEN the author is tempted to compare alternatives at length THEN the guidance limits the output to one line and forbids debate of alternatives and any dedicated rationale section.

**UI/UX Specifics:**
- **View/Component:** Design document, contracts and file inventory.
- **Feedback Logic:** Rationale is visibly marked so it can be found and quoted into worker briefs.
- **Keybindings:** Not applicable.

**Technical Constraints (NFR):**
- **[Integrity]:** Code-symbol anchors stay in the design as the single place they are written; tasks do not repeat them.
- **[Maintainability]:** No new top-level section is added to the design template.

### [US-6] Self-Containment Rule Amended in the Constitution
**User Story:** AS A project owner, I WANT TO align the constitution's self-containment rule with lean specifications, SO THAT the rules and the templates do not contradict each other.

**Scenarios:**
1. **[Happy Path]** GIVEN the constitution's self-containment rule that requires every code-symbol anchor in the whole specification WHEN it is amended THEN it requires self-containment in business rules, intent and decisions, and limits symbol-level anchors to the design and to non-obvious constraints.
2. **[Edge Case]** GIVEN a human has not approved the amended wording WHEN the amendment is proposed THEN the constitution document is not modified.

**UI/UX Specifics:**
- **View/Component:** Engineering constitution document.
- **Feedback Logic:** The amendment is presented to the owner for approval before it is written.
- **Keybindings:** Not applicable.

**Technical Constraints (NFR):**
- **[Safety & Security]:** Constitution documents are changed only with explicit human approval.

## 4. Business Invariants
*Strict domain rules that the system must never violate, regardless of the user story. These must be technically testable.*
- Every task keeps a mandatory acceptance check consisting of a single non-interactive command or test scenario.
- Every roadmap that was valid before this feature remains valid after it.
- Warnings never change validity, progress or the outcome of any command.
- The design is the only place where code-symbol anchors and technical rationale are written; tasks reference them instead of repeating them.
- Workers receive design excerpts verbatim and never invented ones.

## 6. Global Non-Functional Requirements (NFRs)
*Technical constraints and quality gates. Aligned with .specforce/docs/engineering.md*
- **[Performance]:** Specification and implementation status keep a single pass over the artifacts, with no additional files read except the design when building a worker brief.
- **[Reliability]:** Behaviour is deterministic for the same input and identical across supported agents.
- **[Security]:** The constitution is modified only after explicit human approval.
- **[Maintainability]:** Behaviour changes are covered by automated tests for validation, warnings, legacy compatibility and brief generation.
